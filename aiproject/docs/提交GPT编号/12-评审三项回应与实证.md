## §1 身份与鉴权 — 评审正确，我们更正表述

### 1.1 评审观点（我们完全认同）

- 共享 `Bearer` 只说明 **调用方持有服务间密钥**，不能证明 **员工本人**。
- 当前 `require_employee` 在校验 Bearer 后，**直接信任请求头 `X-Employee-Id`**（见 `app/core/auth/dependencies.py`）。任意持有 token 的客户端可填 `X-Employee-Id: 999`，API 会将其当作操作者 — **与「可信网关绑定、调用方不可改写身份」不满足**。
- `owner_employee_id` 校验仅能防止「A 的员工头去改 B 负责的单」，**不能**防止「伪造员工 999 创建并占有客户」类问题（若业务允许 `owner_employee_id` 与头不一致时尚需另查路由校验）。

### 1.2 当前实现的准确命名（避免再写「鉴权已通过」）

| 能力 | 实际做到 | 不能宣称 |
| --- | --- | --- |
| 无密钥不能调业务 | 无/错 Bearer → 401；未配置 token → 503 | 「员工已登录」 |
| 负责人改状态 | 操作者 `employee_id` 须等于 `owner_employee_id` → 403 | 「身份来自 SSO」 |
| 过渡方案 | `AUTH_BEARER_TOKEN` + 头 | 「生产可信身份」 |

### 1.3 达到「已验证」身份所需的集成契约（待负责人拍板，我们未擅自实现）

1. **网关 / 公共 auth** 校验员工 JWT 或会话后，向 API 注入 **不可由客户端覆盖** 的身份（例如内网签名头 `X-Internal-Employee-Id`，或 JWT 内 `sub` 与 API 侧验签）。
2. ENT 模块 **删除或忽略** 客户端提交的 `X-Employee-Id`（或仅当与 token claims 一致时采纳）。
3. Dify → API 场景：Dify 仅持服务 token 时，**不应**模拟员工；应由网关在员工登录链路后转发。

**阻塞项**：公共 `modules/auth` 未就绪 — **身份链路仍为「未验证」**；R2 HTTP 只证明 **服务密钥 + 业务读写 + 401**。

## §2 数据库边界 — 31 表与 DROP 的补充说明

### 2.1 作用范围（硬边界）

| 环境 | 是否执行 `db_init.sql`（含 DROP） | 说明 |
| --- | --- | --- |
| 本机 `127.0.0.1` / 库名 `education_service` | **是**（2026-11-11） | **可丢弃的本地联调库**；非腾讯云、非同学共享库 |
| 腾讯云 Docker MySQL | **否** | 未连接、未执行任何 DDL |
| 评审要求的「不清库」 | **遵守** | 仅对 **本机开发实例** 使用 DROP；云端与团队约定库 ** untouched** |

### 2.2 执行方式与数据影响

- 脚本：`python scripts/apply_db_init.py`（读 `aiproject/.env` 的 `DB_*`）。
- 行为：按标准文件 `教育服务_0914/2222通过表可以实现curd/db_init.sql` **先 DROP 再 CREATE**，共 **31 表**。
- **影响**：该库内原有数据（含早期 R1 测试行）会被清空；之后 HTTP E2E 重新写入 `E2E_HTTP_20261111_171814`。
- **承诺**：后续全量 DDL **不在无书面确认的共享/生产库执行**；若需无 DROP 迁移，应由 DBA/集成给出 `CREATE IF NOT EXISTS` 或 Flyway 类流程，**不由 ENT 单方跑 DROP 版**。
