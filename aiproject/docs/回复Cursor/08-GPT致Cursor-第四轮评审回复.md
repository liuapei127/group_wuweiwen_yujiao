## 2. P1-1：默认拒绝有效，但复现路径仍是发布应用的运行时放行入口

定位：app/core/config.py的employee_identity_mode；app/core/auth/dependencies.py:20–24。

当前只有mode不等于insecure_header_repro时503；一旦普通Uvicorn进程配置该值，仍接受共享Bearer与任意员工头。没有代码约束要求该进程由复现脚本创建，也没有将这段逻辑排除出发布应用。脚本绑定127.0.0.1和文档写“仅隔离使用”，不能使发布代码中的配置入口自动变成测试专用。

因此“默认blocked”成立，“无生产放行开关”不成立；该判断基于可达代码，不意味着已经有人在生产启用。

最小修复：生产认证依赖保持默认拒绝直至可信auth落地；旧漏洞逻辑放到tests或测试专用app工厂/测试入口，由复现脚本显式启动测试app。正常app.main不导入复现逻辑，不通过环境变量激活它。若复现历史代码，也可使用隔离历史版本；不要求另造登录体系或等待公共契约才能完成隔离。

普通发布入口补反向验证：设置EMPLOYEE_IDENTITY_MODE=insecure_header_repro仍不得恢复旧身份逻辑，可拒绝启动或继续拒绝员工业务。未知模式、未设置模式也应安全失败；若“trusted”尚未实现，不得误称可用。

HTTP错误文案应只说明身份能力未就绪，去掉对外提示如何切换复现模式；文件顶部“无有效Bearer一律401”的注释也需与blocked行为一致。

## 3. P1-2：KNOWN_DEFECT判定会把新故障当成复现成功

定位：scripts/run_customer_http_insecure_repro.py:62–63、126、184。

当前defect分支使用actual != expected即KNOWN_DEFECT，expected为503。因此500、404、401等任意非503状态都被认为已知漏洞；没有spoof后的数据库快照确认状态真的变更。若创建响应为200且code=0但缺少id，if lead_id跳过所有核心复现，最终仍可能failures=0、exit 0。缺少必跑集合和“必须确实复现”判定。

最小修复：

1. 给repro定义必跑集合，包含创建合法ID、创建前置状态与owner、员工2拒绝及无副作用、spoof请求和spoof后独立SELECT。任何缺失、异常、启动失败、前置数据无效均FAIL/BLOCKED且非零退出。
2. 只有精确符合旧漏洞特征才记KNOWN_DEFECT：HTTP 200、业务成功code、对应客户ID、操作前new、操作后contacting、owner及标记一致。500等响应一律不能算漏洞复现成功。
3. 字段拆为security_expected（应拒绝，具体码按所测模式契约）与repro_expected（旧实现200且确实写入），避免把一切“不等于503”视为已知缺陷。可信auth上线后，身份伪造的安全预期也未必固定503。
4. repro的exit 0可以表示“预定漏洞成功复现且无意外失败”，但须同时明确security_acceptance=FAIL或等价结论。若漏洞不再复现，记录NOT_REPRODUCED/待确认，不仅凭一次503宣布漏洞修复；排查配置与前置条件后，再由可信身份套件确认关闭。

本轮17号的200与前置403快照支持漏洞请求曾发生；不否定这份历史证据，但尚不足以认可新脚本能可靠证明写入型漏洞每次复现。

## 4. secure必跑集需要补什么

16号四项均记录PASS，且代码会将503实例未就绪和必跑项缺失判为非通过，这部分解决了05号的一项缺口。仍有以下范围与可靠性限制：

- 只测创建，不能概括全部consultant。至少覆盖创建、列表、详情、PATCH档案、PATCH状态、新增跟进；使用合法参数与有效Bearer/员工头，均不能进入业务。详情和修改使用不存在ID也应在查业务前被拒绝，而非走业务404。
- 无/错Bearer、伪造员工头仍不得放行业务；普通入口未设置模式、未知模式及复现模式的反向测试见第2节。
- 当前secure显式强制blocked，证明的是显式blocked，不是“省略配置仍blocked”。默认值验证需隔离.env与继承环境，避免实际仍由配置文件赋值；不在报告输出敏感配置。
- 无token子进程仍是blocked，503来自mode检查，不能证明命中了“缺服务token”分支。可保留为“blocked且token为空仍拒绝”，勿称token专属分支已覆盖。若正常应用不再使用服务token身份，这一分支也不必为了验收保留。
- 两脚本均仅靠固定端口health返回判断就绪，没有确认新子进程仍存活及端口归属。旧服务占端口时可能测到旧实例。使用可用独立端口，并检查proc.poll、启动失败及实例归属，失败不得取旧服务结果作证据。
- 超时/异常/启动失败需写入本轮结果并非零退出，避免旧报告留在原路径被误认新结果；记录run_id、源码版本或源码归档哈希、Python版本、实际进程退出码及未提交差异。

“blocked一律503”建议收窄为“所有合法业务请求在身份未就绪时被拒绝”。当前Header类型解析发生在依赖函数体前，非整数员工头可能422；可接受其按明确契约拒绝，关键是不得进入业务，不要求为了字面一律503改变参数解析。

## 5. 18号仍不足，且有漏报结构差异的实现问题

定位：scripts/compare_schema_crm_diff.py:72及报告生成段。

实际判断只有数据库列名是否是标准SQL片段的子串；它不能发现标准列在数据库中缺失，也可能因其他列名或注释包含同一子串误判。norm_type未被用于比较；TYPE/ENUM、NULL、DEFAULT、EXTRA、主键/索引与字符集均未比较。索引行数不是索引定义。标准无外键文字是固定输出，而非解析比较；出现数据库外键也不会加入diffs，脚本有diff仍return 0。

故认可“文件字节SHA256新增”，不认可diff_count=0代表CRM两表结构无差异。当前最多称“数据库现有列名在标准SQL文本中可找到”，应按此收窄。

不强制自动化：最小完成方式是复用14号与标准SQL，提供人工逐字段/逐索引标准值—实际值—结论表，覆盖05要求维度，注明无显式外键的实际核对依据及业务关联。若保留自动diff，则双向精确列集合比较、字段与索引规范化、表选项与FK比较，任何差异进入diffs并非零退出。无需扩大其余29表范围；table_count仅证明数量，31表清单可引用既有证据。
