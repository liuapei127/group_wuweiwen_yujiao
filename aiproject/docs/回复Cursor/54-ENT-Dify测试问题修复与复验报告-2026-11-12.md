## 修复内容

| 问题 | 修复后的行为 |
| --- | --- |
| 已发布 v1 仅含客户创建/列表；旧 v2 对标记后的空格、多行 JSON 解析失败 | 生成 v3 图，严格解析最终 JSON；兼容 ENT_ACTION、JSON 代码块和模型 think 包装；无关键词补写、无“未解析姓名” |
| 缺字段、功能咨询或否定表达可能被当作写入 | 缺字段追问；否定/未知动作不请求；只有列入目录且参数验证通过才进入固定 HTTP 方法分支 |
| 无明确写入确认、重复确认风险 | conversation.pending_action 保存待处理动作；展示参数后要求明确确认；取消清空；提交前清空，重复确认不再次提交；写请求不自动重试 |
| 姓名操作缺少编号判定 | 先按姓名查询候选，等待选择编号，再对写入要求确认；不自动选择第一条 |
| employee_id/owner 写死为 1 | 移除 Dify 固定员工身份字段；客户、跟进、日报、审批的 actor 可省略，但只能由后端可信 principal 推导；显式其他员工 ID 仍受权限检查 |
| 模型可能提前声称成功、错误统一伪报为 503 | 只依据真实 HTTP 和业务响应；写入必须为 2xx、code=0、存在正整数记录 id；分别处理 403/404/409/422/503，网络错误不伪装为 503 |
| 成绩更正缺少前端版本约束 | Dify 更正要求 expected_version；409 要求重新查询，不自动重试更正 |
| MySQL 扫描出现 1213 重试耗尽 | 同一数据库用独立连接持有扫描 GET_LOCK 到事务结束；其他扫描者本轮跳过；候选 JOIN 不加范围锁，按源记录主键顺序锁定后同步；保留有界随机退避 |
| 旧验收脚本可能仅看子进程退出码 | 基础检查同时验证状态和响应语义；Dify 对话另查 SSE、调用次数、实际动作、持久化节点记录和发布版本 |

代码继续按 docs/architecture.md 分层：HTTP 绑定和可信身份推导在 router，业务权限和事务在 service，扫描 SQL 与锁在 todo/reminder_repository.py，AI 纯契约在 app/ai/workflows/ent_contracts.py。CRM 主键增加 SQLite 类型适配，MySQL 仍使用 BIGINT，以便隔离集成测试真实执行自动编号。

## Dify 环境恢复及数据保留

现场同时存在 dify 与 docker 两套 Compose 容器，PostgreSQL 和 Redis 指向相同宿主机数据目录；Redis 原 dump.rdb 校验失败。共享目录并行运行存在损坏风险，但仅凭该现场不能认定它是快照损坏的唯一原因。

处理前完成 PostgreSQL 逻辑备份（1,679,219 字节，SHA256 681fe7327f7828aba55e275a6ef448d5b680ac8317e325a82dfd91129d75c2a3），并备份损坏的 Redis 快照和原运行配置。备份位于忽略的 logs 目录，不在本报告展示密钥。

停止重复 docker 项目并关闭其自动重启，未删除容器或业务数据卷；外部 D:/tools/dify-1.16.0/docker/.env 固定 COMPOSE_PROJECT_NAME=dify。新增 docker-compose.override.yaml 让 Redis 使用 ent-recovered-20261112.rdb，原 dump.rdb 保留原位，项目内另有备份。Redis、PostgreSQL、API 和沙箱现已健康，SSRF 代理至宿主 API 的请求已恢复。

**旧 Redis 缓存和登录会话未恢复，控制台可能需要重新登录。** PostgreSQL 的应用和旧工作流仍保留；没有创建新的 API 密钥、重置业务库或放开 ENT 认证。
