## 3. 本轮仍需修正的具体问题

### 3.1 反向启动测试会因无关失败误报PASS

run_customer_http_secure_matrix.py中main_rejects_insecure_mode只判断两秒后进程是否退出；任意退出码、依赖导入错误、配置错误甚至无关异常都可能PASS。stderr虽设PIPE，却没有读取并判断预期原因。

补为：有界等待并收集stderr，确认非零退出且原因为预期的insecure模式拒绝；同时确认该端口没有启动可用业务服务。超时或其他错误必须FAIL/BLOCKED。日志脱敏后保留可核对的拒绝原因。不要只把exit_code=1当作预期异常的充分证据。

此处是测试证明力缺口，不推翻生产依赖已移除不可信逻辑这一代码事实。

### 3.2 P1测试与证据收尾

- secure目前显式设置blocked，未证明无配置默认行为。补独立Settings/启动测试，隔离.env与继承变量，确认默认blocked；未知模式拒绝启动，trusted_jwt未实现时仍拒绝。不要改写现有.env来造默认场景。
- secure档案PATCH使用customer_name，但当前LeadUpdate不包含该字段。改为真实允许的contact_info、intended_country等字段，避免未来参数校验调整后测试失去明确含义。
- HTTP/JSON/数据库异常可能抛出后未写本次报告，旧16/17文件仍在。异常时也输出本轮run_id及失败记录、非零退出；保留独立运行产物或清楚标记“本轮未产出”，不能把旧报告当新结果。
- run_id目前是报告标识，不是服务端实例归属证据。现有动态端口加存活检查已是实质改进；后续可通过测试专用实例标识或监听socket继承等证明所属子进程，不必为此增加公开生产接口。
- 补同一源码版本、未提交差异或源码归档哈希。process_exit_code/exit_code目前由脚本计算并写入后再return，可说明为计算退出值；实际调用方退出码另记录。16/17覆盖写入时保留旧run归档，便于追溯。

### 3.3 测试app目前修改生产app单例：需避免同进程污染

该项定位于tests/repro/asgi_app.py：from app.main import app后直接修改app.dependency_overrides。当前复现脚本使用独立子进程，所以没有证据表明它污染了正常服务进程；不把此项重新当作已关闭的环境变量漏洞。

但同一个pytest或其他Python进程先导入tests.repro再使用app.main.app时，共享单例会残留不可信覆盖。建议用独立测试FastAPI实例并注册路由，或app工厂每次创建新实例；测试后清理覆盖也需finally保证。补一条“同进程导入测试入口不改变生产app覆盖集合/认证行为”的隔离检查即可。正常app不主动导入复现入口的边界继续保持。

### 3.4 19号仍是抽查摘要，不是完整逐维差异表

19号已明确“抽查维度未发现差异”，这一收窄可接受；不能把10号“用人工表满足最小交付”视为完整关闭CRM核对任务。

目前仅列crm_lead四个代表字段及crm_follow_up若干字段，ENUM用省略号，其余字段仅一句“肉眼一致”。NULL/DEFAULT/EXTRA、主键与索引列顺序及唯一性等缺少完整标准值和实际值。

最小补齐：两表18+7字段逐行列出类型/完整枚举、NULL、默认值、EXTRA及结论；索引含PRIMARY、列顺序、唯一性；表级字符集/排序规则；实际FK与应用层关联。可以复用14号数据和标准SQL做人工核对，不要求重写自动解析器，不要求扩大到其他29表，也不要求再次初始化数据库。若只保留抽查结论，则CRM完整兼容性继续未验收。
