## 2. 按优先级列出的问题

### P1：当前员工身份仍可冒用，不能仅以“阻塞”替代默认拒绝

app/core/auth/dependencies.py:33仍直接将客户端X-Employee-Id构造成EmployeePrincipal；13号中spoof请求200且状态转为qualified，与缺陷描述一致。登记方式没有掩盖结果，这一点接受。

公共auth未就绪期间，服务Bearer可保留在已明确授权的服务身份能力中，但不能借员工头取得员工权限。员工业务在可信身份校验能力未就绪时应默认拒绝，可使用503表达服务能力未就绪；可信认证已就绪后，无/错凭据用401、有效身份但权限不足用403。无需把所有接口一律503，健康检查按原契约保留。

本地漏洞复现版本及证据可以保留；若继续使用可伪造方案进行隔离实验，必须明确是缺陷复现，不能作为可合并发布的默认员工认证实现。不新增生产放行开关。正常业务授权逻辑可通过仅在测试代码中的依赖覆盖继续验证，单列为应用内测试。

### P1：矩阵可能漏报失败，exit 0不能作为完整验收结论

定位：scripts/run_customer_http_matrix.py:255–288、305–326。

1. happy_list、happy_detail、happy_status、happy_detail_after只有HTTP日志，没有进入matrix_results逐项断言；happy_create只按HTTP 200判定，未将业务code、返回ID和内容契约纳入通过条件。当前日志可人工检查，但脚本不能据此保证后续回归正确。
2. db_ok只要求首行状态属于qualified或contacting，未严格核对唯一行、创建ID、owner和确定的预期终态。本次qualified来自spoof缺陷请求，应明确标为“漏洞导致的修改”，不能写成另一次已授权的正常流转。
3. 503实例健康等待失败时不写失败项；最后all只检查已有结果，可能跳过必跑的503用例后仍exit 0。缺少lead_id时也跳过若干用例，必须有预定义必跑集合与缺失检查。
4. 正常实例无Bearer允许401或503、非法枚举允许400或422，比本轮明确契约更宽。应分别锁定401和422，缺配置实例单独锁定503。
5. spoof项passed硬编码False，identity_defect_recorded仅检查用例名称存在，没有从实际响应及前后数据确认缺陷是否复现。修复后也无法自动识别缺陷关闭。

要求：逐项保存expected、actual、outcome；区分PASS/FAIL/KNOWN_DEFECT/BLOCKED/SKIPPED。回归子集可单独输出通过状态，但总体验收应保持失败或阻塞。可分开“业务回归”和“漏洞复现”命令；后者证明漏洞存在不等于安全验收通过。将expected_case_set完整性纳入退出条件，503进程启动失败不得静默跳过；检查子进程仍存活和端口归属，避免旧实例冒充本次启动实例。

## 3. 对15号五个问题的直接答复

1. 过渡Bearer可作为服务凭据保留，但不能将客户端员工头作为员工身份。不是单纯禁止某个头名，而是任何不可信字段都不得决定操作者。可信能力缺失时员工业务默认拒绝；无需将健康接口一律503。
2. spoof登记已满足“不计权限通过”的材料要求。但请修正硬编码缺陷判定与整体退出语义，并保留前后数据证据；当前整体仍存在已知身份缺陷。
3. CRM范围足够，不要求29表抽检；缺的是两表的实际逐维比较结果，不是更多原始采集。
4. 接受CI或他机Python3.11证据。一次exit 0本身不够：同一明确源码版本、普通与editable两个独立干净环境、命令及完整退出码、安装后import；普通安装从源码目录外执行import。保存SHA及未提交差异/源码归档哈希，避免日志与提交内容不一致。Docker另记，不互相代替。
