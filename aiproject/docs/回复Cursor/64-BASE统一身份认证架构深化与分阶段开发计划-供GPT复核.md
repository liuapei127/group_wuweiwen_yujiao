## 3. 统一认证目标架构

公共进程仍是 `aiproject`。身份只有四类，不合并：

- 员工：`user_type` 为 `employee` 或 `admin`。
- 学生：`user_type` 为 `student`。
- 访客：无账号令牌，只访问明确的公开读或报名接口。
- 服务：`typ=service`，没有员工编号，不能代表某个员工。

| --- | --- | --- | --- | --- | --- | --- |
| 员工身份 | `sys_user`，创建和停用在 `/api/v1/auth/users` | 表、哈希、停用后撤销 | 组织成员关系 | 现有用户表 | 现有用户接口 | 停用后旧令牌被拒绝；不新建用户表 |

每个受保护请求的顺序固定为：验签和 claim → 按 `sid` 查会话 → 按用户状态和类型装入主体 → 进入原业务 service。前三步失败则不会写业务数据。

## 4. JWT 技术比较及推荐

| 方案 | 多模块安全性 | 密钥分发 | 性能 | 依赖和兼容 | 结论 |
| --- | --- | --- | --- | --- | --- |
| HS256 | 验签方必须持有签发密钥，任一模块泄露就能伪造全组令牌 | 对称密钥要发给每个验签进程 | 最快 | 当前环境已支持。8002 正在使用 | 只保留给现有 `ent-portal` 过渡 |
| RS256 | 私钥只留在 BASE 签发进程；模块只持公钥 | JWKS 或公钥文件。公钥可以公开 | 对登录和每秒有限的 API 足够 | PyJWT 在安装 `cryptography` 后支持。库和文档最常见 | **推荐为 BASE 新令牌** |
| ES256 | 同样是私钥签发、公钥验证。密钥更短 | 同样走 JWKS | 签名更轻 | 也依赖 `cryptography`。课程环境里的网关和示例更少 | 不作为第一选择 |
| EdDSA | 签名短，算法现代 | 同样走 JWKS | 轻 | 当前虚拟环境没有对应算法。PyJWT 需 `cryptography` 才可能启用。组内没有现成工具链 | 依赖未具备，本阶段不选 |

推荐 RS256 的理由：五个模块只需要验证，不应该每人持有能签发的密钥。RS256 把私钥留在 BASE。当前代码和虚拟环境还不能签 RS256，所以实施时要显式加入 `cryptography`，并保持算法白名单，继续拒绝 `none`。实施前不改代码。

**建议中的新令牌，不是把旧令牌改名：**

| 字段 | 设计 | 依据和限制 |
| --- | --- | --- |
| `iss` | `edu-base` | 与 `ent-portal` 区分。模块确认前不写入生产配置 |
| `aud` | `education-api` | 表示这一套共享 API，不用 `ent-api` |
| `alg` | RS256 | 见上表 |
| `kid` | 密钥编号 | 只在 BASE 公钥上使用，供轮换 |
| `sub` | `sys_user.id` 的十进制字符串 | 沿用现有主体。不接受调用方另传员工号 |
| `sid` | 会话 UUID | 对应 `ent_auth_session.id`，用于撤销 |
| `user_type` | `employee`、`admin` 或 `student` | 来自数据库，不来自请求体 |
| `role` | `sys_role.role_code` | 只标识角色。员工权限仍在每次请求时从 ENT 权限表读取，避免令牌里的权限过期或不该扩散 |
| `iat` / `nbf` / `exp` | 签发、生效、过期 | access 继续最长 60 分钟 |
| 组织 | **不放入令牌** | 成员表尚未存在。字符串 `department` 不能当成部门权限 |

过渡期验证器同时认识两类 access：`ent-portal` + HS256，以及将来的 `edu-base` + RS256。前者只服务已经发出的门户会话。新登录在 BASE 签发上线后改发后者，8002 页面和 RBAC 不推倒。

## 5. 员工和学生身份隔离

员工登录保持 `POST /api/v1/auth/login`。只接受 `employee` 和 `admin`，学生密码正确也返回同样的 401。

学生登录使用 `POST /api/v1/auth/student/login`。只接受 `user_type=student` 且状态正常。签发的令牌 `user_type=student`，不带员工权限，也不进入 `require_employee`。

员工接口声明 `require_employee`。学生令牌在类型检查处被拒绝，到不了审批 service。学生接口声明 `require_student`，主体里的学生编号只取令牌对应的 `sys_user.id`。员工令牌不能调用学生提交接口。管理员若要代办学生业务，必须走员工管理接口并留下审计，不能把 `user_type` 改成学生。

CS 访客不登录。课程查询、政策问答和活动报名若对访客开放，路由不使用员工或学生依赖。访客接口必须在设计时列出白名单；未列出的写接口保持拒绝。

## 6. 角色和组织设计

BASE 提供身份和组织基础数据。PF、CS、ENT、STU、RPT 各自判断业务动作。`crm:write`、`leaves:approve` 等码留在 ENT，不改名为全组通用码。

建议新增 `sys_org_member`：

| 列 | 含义 |
| --- | --- |
| `user_id` | `sys_user.id` |
| `org_id` | `sys_organization.id` |
| `is_primary` | 是否主部门。同一员工同时只有一个主部门 |
| `effective_from` | 生效时间 |
| `effective_to` | 可空，结束时间 |
| `status` | `active` 或 `inactive` |

一个员工可以属于多个组织，例如主部门和项目组。主管不另建上下级表：`sys_organization.manager_id` 指向负责人；其下属是该组织及下级组织里的有效成员。借调或虚线汇报等规则现在没有需求，不提前建模。

在成员数据写入并核对之前，身份主体不返回“可管理部门”或“可看全部门客户”。ENT 继续用负责人字段和学生授权范围做数据权限。

## 7. Token 生命周期

**Access Token** 是短时 JWT。业务进程先验签，再按 `sid` 读取 `ent_auth_session`。签名有效但会话缺失、已撤销或已过期，都拒绝。这样撤销不必等 `exp`。

**数据库依赖和 fail-closed：** 每次受保护请求都会查会话。这是一次按主键读取，量级可接受。会话库不可用时沿用现在的做法：捕获连接或表错误，返回 503，不降级成“只验签名就放行”。只验签名会让登出和停用失效。

**Refresh Token** 是随机串，库中只存哈希，绑定用户、会话和过期时间。`POST /api/v1/auth/refresh` 校验哈希后签发新的 access，并轮换刷新串：旧哈希立即作废。重复使用已作废的刷新串时，撤销该会话家族并记审计。

**登出** 撤销当前 `sid`。**改密和重置密码** 撤销该用户全部会话。**停用账号** 把 `status` 改为 `disabled` 并撤销全部会话；之后即使令牌签名正确也失败。**会话到期** 以 `expires_at` 和 JWT `exp` 中先到达者为准。

**密钥轮换：** 新 `kid` 负责签发，旧 `kid` 在一个 access 有效期窗口内只验证。窗口结束后从 JWKS 移除旧公钥。私钥泄露时立即停用该 `kid`、撤销全部会话，并要求重新登录。刷新令牌哈希一并作废。

**审计：** 成功登录、登出、刷新轮换、改密、停用、密钥切换记入 `ent_auth_audit`。失败登录只增加 `ent_auth_login_attempt`。

## 8. 服务间认证

服务账号不是员工，也不是学生。令牌 `typ=service`，`sub` 是客户端编号，不包含 `employee_id`、`user_type` 或组织。验证时核对 BASE 签名、接收方、过期时间和客户端是否启用，不把服务令牌送进 `require_employee`。

现有 `AUTH_BEARER_TOKEN` 不能继续解释成“持有它就可以填员工号”。04 号已经记录这条历史缺陷。新设计里，服务身份若要代员工操作，必须另有用户委派的 access，并且审计同时记下服务客户端和员工 `sub`。没有委派时，服务令牌只能调用明确列出的非员工接口，例如健康检查或不含个人数据的内部任务。该委派规则仍要相关模块确认后才实现。

## 9. Dify 身份传递

比较两种做法。

**方案 A：门户后端代发。** 员工在 8002 登录，浏览器只保存自己的 access。门户把对话文本交给 Dify，Dify 只返回意图；真正写库由门户用该员工的 Authorization 调用业务 service。模型提示词里没有令牌，也没有可被模型改写的员工号。这是当前门户 AI 已验证的路径。

**方案 B：公开 Chatflow 的 HTTP 节点自己带身份。** 若把令牌放进对话变量或让模型生成请求头，模型就能看见或改写身份。若在 HTTP 节点配置一把固定密钥，则这把密钥代表服务而不是当前员工；再配固定员工号就会回到冒充。Dify 的终端用户标识由调用方传入，也不能单独当成已验签的员工。

**推荐方案 A。** 员工写操作只从已登录门户进入现有 service、权限检查和事务。公开 Chatflow 在出现模型改不了的、且能对应到已验签员工的通道之前，继续只做探活；8000 对业务请求保持 503。本轮不改 Dify 配置，不发布工作流。

| `backend/app/main.py` | README 中的 `uvicorn app.main:app --host 0.0.0.0 --port 8000` | 与正式 API 冲突的 8000，且监听所有网卡 | 两个 compose 文件都没有引用 `backend/` | 客户、请假、报名、成绩等路由只有数据库依赖，调用方可以在查询参数里带审批人或负责人 |

云上文档写明 `backend/` 是参考实现，不是运行真相。仓库里没有根级 `compose.yaml`，因此文档中的云上完整启动命令目前无法在本仓库原样复现。

**处置，先不删代码：**

1. 演示和 Dify 只连接 `aiproject`。
2. 不把 `backend/` 加进 compose。
3. 启动前确认占用 8000 的进程是 `aiproject`，避免旧进程以 `0.0.0.0:8000` 接走流量。
4. 后续单独提交时，在 `backend/README.md` 标明“非运行入口”。本轮不改该文件。
5. 旧路由保留供对照，直到确认没有文档或脚本仍以它为演示入口。

旧入口是绕过新身份的实际路径，但只在有人按 `backend/README.md` 启动它时发生。compose 本身不会把它拉起来。

## 15. 风险、依赖和待确认项

**风险**

- 过早 `git add` 会把 `.env`、日志或门户凭据送进仓库。
- 旧 `backend/` 若占上 8000，会在无身份的情况下写业务表。
- 把组织字符串或 ENT 权限码写进全组令牌，会造成过期授权和跨模块越权。
- 会话库故障时若改成只验签，登出和停用会失效。
- 为公开 Chatflow 写库而关闭 8000 的默认拒绝，会使模型或伪造头成为员工身份。

**依赖**

- P2 依赖在 `aiproject` 环境加入 `cryptography`。当前未安装。
- P1 依赖 Gitea 账号能够 `git fetch`。当前认证失败。
- P7 依赖各模块给出自己的权限规则。BASE 不代替他们编写业务授权。

**仍由相关模块确认，不阻塞 BASE 把方案写成设计**

- PF：上传和查看研判结果的员工范围。
- CS：哪些接口真正对访客开放。
- STU：学生账号是否就是 `sys_user` 中 `user_type=student` 的行。
- RPT：主管可以看到哪些报告行。
- 全组：`edu-base`、`education-api` 和 RS256 是否作为实施时的签发方、接收方和算法。未确认前不写入生产配置。

本轮没有修改业务代码、认证逻辑、数据库、生产配置、Dify 工作流，也没有把任何目录加入 Git。
