## 0. 一分钟：这个项目在干什么

公司里顾问通过 **Dify 对话框（AI）** 说话，AI 帮他把意图变成「建客户、查客户、写跟进、批请假、查数据」等动作；真正读写数据库的是我们写的 **FastAPI 后端**。

- 数据库：团队统一的 **31 张表**（`db_init.sql`），MySQL，库名多为 `education_service`。  
- **ENT 负责**：接口、安全与测试、文档。  
- **ENT 不包办**：公共登录/JWT、腾讯云部署操作、学生端请假提交——需要对应负责人一起完成。

---

## 1. 四句话总结（开场可直接念）

1. **客户管理相关接口，本地代码基本写好**，在专用测试环境里做过权限类 HTTP 验证（不能看别人客户等）。  
2. **正式入口 `app.main` 上所有员工业务（客户、日报、请假、指令、NL2SQL）默认 503**；2026-11-11 已统一 `require_employee`，不再只有客户模块上锁。  
3. **云上目前主要是健康检查**；业务 API、Dify 真联调、请假/投诉全流程 **都还没验收**。  
4. **Python 3.13** 本地虚拟环境与 Docker 构建已有证据；**关键阻塞是登录契约 + 上云 + Dify 对话流**。

## 2. 怎么判断「做完没有」（四个词）

| 词 | 意思 |
| --- | --- |
| **已实现** | 代码仓库里能看得到 |
| **已测试** | 有日志/脚本/归档，能追溯 |
| **已部署** | 腾讯云 API 能访问到 |
| **已验收** | 业务 + 安全 + 联调被认可，能对外说「这条线 OK」 |

很多项停在「已实现」或「已测试」，还没到「已部署/已验收」。

## 4. Dify 和后端谁干什么（新人版）

- **Dify**：听懂人话、追问缺的信息、决定调哪个 HTTP、展示结果。  
- **FastAPI**：校验权限、改库、返回标准 JSON/HTTP 状态码。  

常见情况：**后端接口好了，Dify 工作流还没配** → 产品上还很难说「助手已经能用」。

## 5. 和其他模块怎么配合（交互 + 对各模块的要求）

这一节给新人：**谁跟谁说话、通过什么通道、ENT 需要别人交什么、别人会找 ENT 要什么**。

### 5.1 总链路（先记这张图）

```text
员工 / 顾问
    ↓ 打字或语音
Dify「企业智能助手」Chatflow（云端 Docker）
    ↓ HTTP Request（内网地址）
http://education-api:8000/api/v1/...
    ↓
FastAPI 容器（aiproject，ENT 写业务接口）
    ↓ SQL
MySQL 8 · 库 education_service · 31 张表（全队共用一套）
```

- **本机开发**：Dify 不能写 `education-api`，要用 `http://127.0.0.1:8000`。  
- **LLM 不许直连数据库**：查数只能走 ENT 的 **NL2SQL 白名单接口**。  
- **一个后端服务**：大家都在同一个 `aiproject` 里加 `modules/*`，通过 `router_registry.py` 挂路由，**不要另起第二个 FastAPI 服务**。

### 5.2 五块业务分工（和大致目录）

| 模块 | 干什么 | 后端目录（习惯） | 和 ENT 关系 |
| --- | --- | --- | --- |
| **ENT 企业助手（你）** | 客户、日报、请假批、NL2SQL、企业指令 | `modules/consultant`、`employee_report`、`student_admin`、`enterprise_ops`、`ai/nl2sql` | 本模块 |
| **STU 学生助手** | 学生端请假提交、投诉、学籍相关 | `modules/student` 等 | **强依赖**：请假/投诉要两端一起通 |
| **CS 客服** | 客服对话、offer 等 | `modules/offer` 等 + RAG | 弱依赖；别改 CRM 表结构不通知 |
| **PF 客户研判** | 研判工作流 | `modules/` 新增 | 弱依赖；共用客户表时要对齐字段 |
| **RPT 报告/统计** | 日报汇总、统计看板 | `modules/statistics` 等 | **中依赖**：日报 JSON 格式要对齐 |

Dify 侧一般是：**每个大模块各有一个 Chatflow**；ENT 配「企业助手」那条，HTTP 节点指向 ENT 接口。

### 5.3 公共 auth / 集成（**当前最大阻塞**）

| 项 | 说明 |
| --- | --- |
| **交互方式** | 员工打开 Dify/前端前应先登录；网关或 auth 模块发 **JWT**；API 只信验签结果，**不信**客户端自填 `X-Employee-Id`。 |
| **ENT 需要对方交付** | ① JWT 里员工 ID 用哪个字段（如 `sub`→`sys_user.id`）；② issuer/audience/算法/JWKS；③ 停用员工返回 401 还是 403；④ 网关注入哪些头、是否禁止直连 API；⑤ **Dify 用服务账号调 API 时**，怎样表示「代表哪个员工」、审计记什么。 |
| **ENT 给对方** | 契约落地后：实现 `trusted_jwt` 模式、`require_employee()` 从 token 取人；consultant 从 503 改为正常业务；补 **伪造身份** 等安全用例。 |
| **ENT 不能擅自做** | 临时登录页、生产环境开「随便填员工号」、自己造 `modules/auth` 一言堂。 |
| **书面材料** | `docs/回复Cursor/04-认证阻塞项与契约待决.md`（三栏表待负责人填「确认」列）。 |

**对集成负责人的明确要求**：指定 **一个人** 拍板上述表格，并在组内 @ 出来；未定前 ENT 只能维持 **blocked（503）**。

### 5.4 Dify（企业 Chatflow 负责人 ↔ ENT）

| 方向 | 内容 |
| --- | --- |
| **Dify → ENT** | HTTP 调 `POST/GET …/consultant/*`、`employee-reports`、`nl2sql/query`、`enterprise/commands` 等；Body 用 **已结构化 JSON**（客户字段、日报字段、`intent`+`params`）；**禁止** NL2SQL 传 `sql`/`raw_sql`。 |
| **ENT → Dify** | 稳定的上云 Base URL（`http://education-api:8000`）；接口文档/Swagger；错误时 **真实 HTTP 状态码**（403/404/409），方便工作流做失败分支。 |
| **ENT 需要 Dify 交付** | ① 企业助手 Chatflow 配好节点（录入/查询/跟进至少一条能跑通）；② 失败分支不能说「已成功」；③ 语音日报：**转写+抽字段在 Dify**，别把「语音完成」甩给后端；④ 身份定稿后 HTTP 节点带 **Authorization**（按 auth 契约）。 |
| **联调节奏** | 建议每天固定一次：Dify 改 HTTP 节点，ENT 用 Swagger/脚本对照；见 `backend/docs/腾讯云部署与小组协作.md` §5。 |

## 7. 两套「入口」——别搞混（P2 与真实身份）

### 7.1 `app.main`（以后要上的门）

- 员工业务依赖 `require_employee()`。  
- 当前：**没有可信登录 → 客户 / 日报 / student-admin / enterprise / nl2sql 一律 503**（`Depends(require_employee)`）。  
- 旧式「自己填员工 ID」**不允许**在 `app.main` 里作生产身份（已去掉上述路由对 `X-Employee-Id` 的依赖）。

### 7.2 `tests.repro`（演习场）

- 故意保留旧式请求头，专门测：**列表隔离、PATCH、跟进冲突** 等业务规则。  
- 评审对这部分给了 **限定阶段签收**（见 `29`/`31` 号材料）。  
- **不等于** 生产 + 真实 JWT 已安全。

### 7.3 什么叫「app.main 真实身份回归」

公共 auth 接好后：

1. 用 `uvicorn app.main:app`（或云上同一镜像）启动；  
2. 带 **真实 JWT/会话** 调客户等 API；  
3. 把 P2 同类场景再跑一遍 + 伪造 token、停用账号等；  
4. 报告里单独写「生产入口 + 可信身份」，不与 repro 层混为一谈。

## 11. 建议下一步（谁干什么）
