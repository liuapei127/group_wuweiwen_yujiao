## 三、必须核查与修复的问题

### 1. 不传员工ID即可更新状态

报告记录：状态更新不带X-Employee-Id可成功；携带不匹配的ID才拒绝。这表明身份检查是可省略的，不应描述为“未绕过鉴权”。

应将报告改为：

> 当前接口尚未实施可信身份认证。状态更新测试仅验证业务读写，不代表权限验证通过。

目标行为：

| 请求场景 | 预期 |
| --- | --- |
| 无凭据或凭据无效 | HTTP 401，业务不执行 |
| 可信身份有效，但无权操作该客户 | HTTP 403，业务不执行 |
| 可信身份有效且符合权限 | 进入业务校验与操作 |
| 客户不存在 | 在认证通过后按统一策略返回404；涉及防枚举时统一说明策略 |
| 非法状态或非法状态转换 | 参数问题422，业务状态冲突409，按统一契约明确区分 |

后端身份必须由可信凭据解析，不得直接相信客户端、Dify模型传来的employee_id或role。
不要允许“不带X-Employee-Id就跳过权限判断”。

公共auth尚未实现时：
- 在实现中默认拒绝未认证业务请求。
- 测试可通过依赖注入显式提供测试身份，但只在测试代码中覆盖。
- 真实HTTP验收应使用实际可验证凭据；尚无公共认证则如实标注阻塞。
- 不增加用于生产跳过鉴权的开关，不将测试身份固定写入业务代码。
- 与集成负责人确认认证契约，避免另建互不兼容的登录体系。

### 2. 本地仅两张表，未证明兼容标准31表

本次测试只创建crm_lead、crm_follow_up，而云端使用统一SQL导入的31张表。

请提供这两张本地表与统一db_init.sql的结构对比：
- 字段名称和类型、UNSIGNED。
- 可空性、默认值、枚举值。
- 主键、索引、唯一约束。
- 字符集和排序规则。
- 实际存在的外键及业务关联关系。

不能只用CREATE TABLE IF NOT EXISTS认定结构一致，该语句不会修正已存在表的结构。

在独立、明确命名的测试库验证标准表结构。不得在已有业务库执行DROP TABLE或覆盖数据。若使用原初始化SQL，先审查其中数据库切换和破坏性语句，确保完全隔离。

owner_employee_id=1属于本次测试数据，不能固定为业务默认身份。需要验证它与可信员工身份及真实记录的关系，不默认依赖数据库存在外键。

### 3. 项目安装失败不能只通过单独安装包绕过

报告显示pip install -e .失败后，改为单独pip install依赖。云端Dockerfile执行pip install .，因此存在构建失败风险。

请先保留原始错误，再核查：
- pyproject.toml构建后端、包发现、Python版本及依赖配置。
- app是否能作为包正确安装。
- 是否缺少声明的依赖、包文件或资源。
- 本地Python是否与云端Python 3.11兼容。

在干净虚拟环境中验证项目安装与import。分别核对editable安装和普通安装；不能推断一种失败就必然导致另一种失败。
有可用Docker时再验证实际Docker构建；没有时明确记录未执行，不声明构建已通过。

当前requirements.resolved.txt只是构建时依赖版本记录，不应被当作已完成团队依赖锁定。

### 4. config.py与config目录需要统一

统一环境变量：

### 5. TestClient流程与真实HTTP联调分开记录

TestClient + 真实MySQL验证了应用内部业务流程，但报告里的独立Uvicorn只明确验证了/health/db。

3. 根据返回的客户ID查询详情。
4. 执行合法状态更新。
5. 再次查询，确认状态变化。
6. 使用独立数据库查询核验结果。

不要硬编码id=1，测试应使用实际创建结果。
如需新建测试员工等前置数据，先确认无冲突，只操作本次标记数据，并记录创建与清理方式。

将测试分为：

某一层通过不能代替其他层。

### 6. HTTP错误状态码与业务码

当前报告显示权限失败业务code=403，但HTTP仍为200。请与团队统一错误契约。

- 认证失败401、权限不足403、资源不存在404、冲突409、校验错误422。
- 依赖暂不可用可返回503。
- 不仅在HTTP 200中放一个错误code。
- 不对外返回数据库异常细节、SQL、账号或密码。
- 如果响应格式从数字code=0变为其他格式，先对齐调用方，不自行破坏既有契约。
