## 第一章  我们在做什么

### 1.1 一句话

做一套 **「员工用说话就能办公」的 AI 助手**：前台是 **Dify 对话框**，后台是 **FastAPI + MySQL**，员工用来管客户、写日报、批请假、问数据——**AI 不直接碰数据库**。

### 1.2 不是用来做什么的（避免跑偏）

| 不是 | 说明 |
| --- | --- |
| 不是一个新数据库项目 | 表结构团队已定（31 张），我们主要是 **API + 工作流** |
| 不是只做刘培阳本地 demo | 最终要在 **腾讯云 Docker** 里和 Dify 内网联调 |
| 不是先上登录再写业务 | 业务 API **先写好**；登录用 **公共 auth**，未就绪时 **故意 503 关停** |
| 不是五个独立后端 | **一个** FastAPI，五人分 `modules/`，统一注册路由 |

### 1.3 用户是谁

| 角色 | 典型诉求 |
| --- | --- |
| **顾问/销售（员工）** | 录客户、查跟进、改状态、口语问「张三跟进几次」 |
| **经理（员工）** | 看团队日报、批请假（后期按部门） |
| **学生** | 提请假、投诉（**STU 模块**，ENT 只审批侧） |
| **运维/集成** | 部署 API、配 Dify、接 JWT |

## 第二章  用户怎么用（端到端故事）

下面每条 = **一条产品能力**；实现 = Dify 理解话术 + 调 HTTP + 写库。

### 2.1 故事 A：录入意向客户（ENT-01）

1. 顾问在 Dify 说：「刚电话了王明，想去新加坡，手机 139xxxx。」  
2. Dify 抽出：姓名、电话、意向国家、负责人等。  
3. 调用后端 **创建客户** → 表 `crm_lead` 多一行。  
4. 助手回复：「已登记，客户编号 xx。」

**完成定义**：库里能查到，且 **负责人** 是当前员工，不是别人名下的客户。

### 2.2 故事 B：查客户、写跟进（ENT-02）

1. 「查一下王明的档案」「帮他记一条电话跟进，下次周五回访。」  
2. 查列表/详情；新增 `crm_follow_up`。  
3. **A 顾问不能看到 B 的客户**（权限是产品要求，不是可选项）。

### 2.3 故事 C：客户状态（ENT-03）

签约、流失、跟进中等 → 改 `crm_lead.status`，符合销售漏斗规则。

### 2.4 故事 D：口述日报（ENT-04/05）

1. 员工说今天干了什么。  
2. **语音转文字、抽字段在 Dify**；后端 **只接收 JSON** 写入 `employee_daily_report`。  
3. 经理日后查日报（按人、按日；**按部门后期**）。

### 2.5 故事 E：批学生请假（ENT-09 + STU）

1. **学生在 STU 助手提交** → `student_admin_service` 状态 `pending`。  
2. 顾问在企业助手说「有待批请假吗」→ 列表 → 「同意张三请假」。  
3. 状态变 `approved`，学生端能看到结果（**STU 要完成展示**）。

### 2.6 故事 F：口语查数（ENT-11）

「张三有多少条跟进？」→ Dify 输出 **intent + 参数**（**不许 SQL**）→ 后端白名单查询 → AI 组织回复。

### 2.7 故事 G：一句话办大事（ENT-12）

「把王明标成签约」「同意李四请假」→ 统一 **commands** 解析后调对应写操作。

### 2.8 尚未纳入本期交付的故事

组织架构问答、新人手册、成绩、投诉全流程、到点推送待办 → **表在库里，API/流程未做或后期**，见第六章。

| # | 交付物 | 谁主要做 | 验收人感受 |

### 5.2 数据「谁写、谁读」（联调对表用）

| 数据 | 谁写入 | 谁读取 | ENT 要做什么 |
| --- | --- | --- | --- |
| 意向客户 `crm_lead` | ENT API | ENT、NL2SQL、CS/PF 可能只读 | 保证 owner 权限 |
| 跟进 `crm_follow_up` | ENT API | ENT、NL2SQL | 同客户归属 |
| 日报 `employee_daily_report` | ENT API（Dify 给 JSON） | ENT、NL2SQL、**RPT 汇总** | 字段与 Dify 对齐 |
| 请假 `student_admin_service` | **STU** | ENT 审批、NL2SQL | 只改审批相关字段 |

## 第七章  「开发一天后」我们实际在干什么（澄清）

很多人晕，是因为 **同时在做三件不同的事**：

| 线在做什么 | 具体工作 | 算不算「功能上线」 |
| --- | --- | --- |
| **线 1：写业务** | consultant / 日报 / 请假 / NL2SQL 代码 | 代码在，但 **main 关着** |
| **线 2：保安全** | 503 收口、P2 测试、评审材料 | 是工程必需，不是白忙活 |
| **线 3：接生态** | Dify 本地、3.13、等 JWT、等 STU | **决定用户啥时候真能点** |

**今天不是「功能做完了还不能用」的 bug，而是「安全与契约未到，故意不能对外用」。**

### 7.1 各角色「下一步唯一重点」

| 角色 | 只做这一件最有价值的事 |
| --- | --- |
| ENT 开发 | auth 契约下来后实现 JWT + 开放 API + Dify 闭环一条故事 A |
| Dify | 本地 Chatflow：health 通 + 录客户节点（接受 503 分支文案） |
| STU | 一条请假写入 `pending` 的样例 + 字段说明 |

## 第八章  实现方式（给写代码的人）

### 8.1 后端一条需求怎么落地

1. **schemas**：请求/响应字段与故事一致。  
2. **repository**：只负责 SQLAlchemy 读写对应表。  
3. **service**：业务规则（状态机、owner、冲突）。  
4. **router**：HTTP + `Depends(require_employee)`。  
5. **router_registry**：注册前缀（不要改乱 `main.py`）。  
6. **Dify**：HTTP 调同一 path；本地 Base `http://host.docker.internal:8000`。

### 8.2 Dify 一条故事怎么落地

1. 意图识别 → 2. 参数 JSON → 3. HTTP → 4. 判断 `code` / 503 → 5. 回复模板。  
详见：`客户管理-Dify闭环说明.md`、`本地-Dify环境与联调步骤.md`。

### 8.3 鉴权现状（必读）

- 调 **`app.main`**：员工业务 **503**；只有 **health** 通。  
- 测 **权限逻辑**：用 **repro 脚本/应用**，不要对领导说「已上线」。  
- 将来：**同一套 API**，换成 JWT 后 Dify 带 `Authorization`。
